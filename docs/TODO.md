# Zonix 开发路线图

> 更新：2026-11-16。目标：小而精、带可选简洁桌面的操作系统。
> 本文描述后续工作，不代表功能已经实现。验收场景是完成标准；新增或运行回归测试仍须遵守 [AGENTS.md](../AGENTS.md) 的当次明确授权要求。

## 产品边界

**不安装 Desktop，Zonix 依然是一个完整的命令行操作系统。Desktop 是可选的用户态软件。**

```text
Zonix
├── 内核：进程、内存、文件系统、驱动、通用显示/输入/IPC 接口
├── 基础用户态（必需）：init、shell、命令行工具、系统管理
└── Desktop（可选）：显示与窗口服务、GUI 库、桌面及图形应用
```

- 基础系统能够独立启动、运行程序、管理进程和文件、查看诊断信息、同步数据并关机。
- 内核和 CLI 工具不依赖 GUI 引擎、图形服务、桌面资源；帧缓冲文字控制台仍可作为基础控制台。
- 窗口管理、合成、控件、主题在用户态；内核只提供通用机制及受控设备访问。
- Base 与 Desktop 镜像使用同一个内核，仅用户态软件和启动配置不同。
- Desktop 可从 shell 启动；退出或崩溃后回收资源并恢复可用的命令行显示与输入。
- 第一版聚焦单用户、单 CPU、静态可执行文件和本地文件操作。以 x86 QEMU 为主要交互验收环境，保留 aarch64、riscv64 的构建及规则检查。

## 当前基线与缺口

| 领域 | 已有基础 | 距离目标仍缺少 |
| --- | --- | --- |
| 启动与架构 | x86 BIOS/UEFI、aarch64/riscv64 UEFI；macOS/Linux QEMU 构建运行支持 | 真机逐平台验证，不能以 QEMU 运行结果代替 |
| 内存与调度 | 页分配、虚拟内存、FIFO swap、小对象 slab 堆、抢占式优先级轮转 | 围绕实际负载记录资源基线，暂不更换算法 |
| 进程与程序 | ELF 用户程序加载、用户地址校验、退出与回收基础；已有标准输入输出 FD | 用户态 spawn/wait、argc/argv、明确的 FD 继承和错误契约；当前 fork 只支持内核地址空间 |
| 文件 | VFS/devfs、FAT 文件写入/open 语义、可检查同步与卸载；已通过三架构 QEMU 回归 | 用户态文件工具；突然断电一致性暂缓 |
| 命令行 | 内核线程中的 init/shell、内建命令、文字控制台 | 独立用户态 init/shell 和基本工具，不以“有内核调试 shell”作为完整用户态的完成标准 |
| 图形与输入 | 帧缓冲文字输出、PS/2 与 VirtIO 键盘字符输入 | 显示所有权切换、按下/释放和修饰键事件、鼠标、用户态图形服务与应用 |
| 关机 | sync 命令、在途文件/原始块 I/O 收尾、设备刷新后断电；失败恢复访问 | 真机固件/平台适配；当前不保证突然断电一致性 |

当前用户程序工具链也不等于三架构完整用户态：应补齐最小静态 ELF 运行时和启动 ABI，不把新增 zcc 后端或系统内自举编译列为前置条件。

## 优先级与依赖

同一优先级按表中顺序推进；阶段通过验收后再将下一阶段作为主线。每次只做一个能独立验收的增量。

| 顺序 | 优先级 | 阶段 | 前置条件 | 完成结果 |
| --- | --- | --- | --- | --- |
| 1 | P0 | 文件写入与打开语义（已完成） | 现有 VFS/FAT | 新建文件可实际写入、增长、重开读取 |
| 2 | P0 | 数据同步与有序关机 | 文件与块设备错误契约明确 | 写入落盘后才报告关机成功 |
| 3 | P1 | 用户程序生命周期 | 文件读写基础稳定 | 用户程序可带参数创建子进程、等待并回收 |
| 4 | P1 | 完整 CLI 基础系统 | 用户程序生命周期 | 无 Desktop 的镜像可以独立日常操作 |
| 5 | P2 | 通用显示与输入接口 | 完整 CLI 基础系统 | 图形客户端可安全取得设备并归还控制台 |
| 6 | P3 | 可选 Desktop 最小闭环 | 显示/输入接口、必要 IPC | shell 启动桌面，桌面退出或失败后回到 shell |
| 7 | P4 | 少量实用图形应用与打磨 | Desktop 最小闭环 | 终端、文件浏览、文本编辑完成真实任务 |
| 8 | 后续 | 单一真机适配 | CLI 与 Desktop 主线稳定 | 在选定硬件上验证完整操作闭环 |

### P0-1：文件写入与打开语义（已完成）

> 已完成实现与运行验收：创建/增长、截断到零、追加、读写权限、多句柄元数据刷新及失败恢复均通过 QEMU 回归。接口及错误契约见 [ERROR_HANDLING.md](ERROR_HANDLING.md#file-open-and-fat-io)。

范围：在现有 VFS/FAT 边界补齐创建、增长、截断、追加及读写权限；明确 open 标志、短读写、EOF 和错误返回。不另建一套文件访问实现。

- [x] 补齐簇链分配/释放、文件长度和目录项更新；同一文件的多个打开实例看到一致的大小和内容。
- [x] 明确 FD、打开文件状态与文件元数据各自的所有权，为后续继承与重定向保留正确边界。

验收标准：

1. 新建空文件后能写入内容；超过一个簇的数据可完整写入，关闭重开后字节与长度一致。
2. 覆写、追加、截断、只读打开按约定工作；无效标志或路径返回明确错误。
3. 多个句柄访问同一文件时元数据一致；空间不足或 I/O 失败返回真实写入量/错误，不报告虚假成功，资源仍可正确释放。

- [回归套件](../kernel/test/unit/fs/file_io_test.cpp)复用[内存磁盘夹具](../kernel/test/unit/fs/fat_image.h)，覆盖 512B/8KB 簇、多句柄、打开权限、磁盘满、数据/元数据/FAT 镜像写入故障、尾链接回滚、清理与卸载重试、目录结束标记边界。
- 系统调用回归确认跨页读写、FD 独立偏移、FD 表满时不误截断，以及一笔多页追加只进入后端一次；两个并发进程在设备写入时强制切换，完整记录保持连续，回收后页数与任务数回到基线。

- 验证边界：aarch64/riscv64 未附 userdata，既有用户 ELF 执行用例跳过；新增 P0-1 套件完整执行。现有宿主 VFS/exec/task 测试因固定 x86 头文件无法在本机 ARM 编译，未计入通过结果；仓库没有 `bun lint/tsc` 脚本。

保持明确的功能边界：仅支持 FAT 8.3 文件名，`mode` 参数保留为零，删除打开中的文件返回 `Busy`；I/O 错误不承诺回滚，正常关机落盘及设备缓存刷新由下述 P0-2 完成，突然断电一致性不在本阶段完成范围内。

### P0-2：数据同步与有序关机

范围：补齐可报告失败的文件系统同步、卸载和块设备缓存刷新契约，再接入关机流程。正常关机持久化不等于突然断电一致性，第一版不要求日志文件系统。

- [x] 同步文件数据、FAT 和目录元数据；按设备能力完成缓存刷新。
- [x] 关机时停止新的文件修改、等待在途 I/O、同步成功后再调用架构电源接口。
- [x] 同步/卸载失败保留必要的脏状态与资源所有权，向调用者报告失败，系统仍可诊断和重试。

验收标准：

1. 创建、写入、修改目录后正常关机，以同一磁盘镜像重启，内容及元数据与最后成功操作一致。
2. 同步或设备刷新失败时不宣称安全关机、不直接丢弃脏数据；电源关闭不受支持时保留可用 shell。
3. 用户可独立执行同步，并获得成功或失败结果；关机复用同一同步流程。

完成记录（2026-11-16，本地验收通过）：

- 内建 `sync` 经 VFS 调用 FAT 同步；卸载复用同一路径。FAT 重试待释放簇链和脏 FAT 副本，再执行设备刷新；刷新失败保留待同步状态与挂载所有权。
- `shutdown` 使用同一文件系统同步接口，并刷新全部已注册块设备：冻结文件操作 → 等待完整 syscall（含分页传输）→ 冻结并收尾原始块 I/O → 同步/刷新 → 架构断电。任何准备失败或返回的电源错误均释放本次冻结，控制台保持可用。
- IDE/AHCI 按 IDENTIFY 能力执行无数据阶段的 FLUSH CACHE/EXT；SD 驱动不启用可选缓存，以 CMD13 确认编程结束。未知刷新能力返回 `NotSupported`，不假报落盘。
- 新增 9 项内核场景：易失/持久磁盘视图区分、刷新超时与卸载重试、FAT 镜像失败重试、不支持刷新、关机同步失败、关机租约与控制台、重入拒绝、完整多页 syscall 排空、原始块请求排空。驱动刷新与 VFS 宿主回归合计 27 项通过。
- `scripts/test_shutdown_qemu.py` 使用临时镜像副本；x86 BIOS/UEFI、aarch64 UEFI、riscv64 UEFI 均完成“写入并 sync → 再追加/创建目录项 → 实际关机 → 同盘重启校验 → 再次关机”。QMP 确认 `guest-shutdown`，宿主逐字节复核 65,583 字节文件及空文件。每次启动分别为 **833 / 833 / 823 / 821 项断言，0 失败**；aarch64/riscv64 原有用户 ELF E2E 仍因缺少对应用户程序而跳过，本项存储场景均完整执行。
- x86 BIOS 额外禁用 ACPI：电源接口返回 `NotSupported` 后继续创建、写入并同步文件；833 项断言通过，宿主确认恢复写入持久化，无 guest 关机事件。
- 修复回归暴露的 BIOS 引导代码与 FAT32 FSInfo 扇区重叠；减少 FAT 分配/回滚嵌套，目录扇区及较大测试夹具移出 4KB 内核栈，保留原栈大小。
- 三架构 `make check`、`TEST=0` 生产构建、clang-format 18、脚本语法检查通过。`bun run lint` / `bun run tsc` 已尝试，仓库未定义这两个脚本。
- 串口及 QMP 记录位于 `obj/<arch>/shutdown-<boot>/`；CI 四个 QEMU job 已接入上述关机重启回归。以上为本地验收记录；远端 CI 结果以对应提交的 workflow 为准。

边界：这是正常关机持久化，不提供日志、突然断电恢复或跨文件事务；设备错误可能需要显式复位，恢复访问入口不绕过 Offline/Quarantined 状态。`sync` 当前为内核 shell 命令，用户态工具及 syscall ABI 随 P1 用户态工作推进。架构电源后端仍按文末平台范围支持。

### P1-1：用户程序生命周期

范围：先提供满足 shell 的最小 spawn + wait，不为追求接口齐全提前实现 fork/COW。不得简单移除现有内核 fork 的用户地址空间限制。

- [ ] 为三架构定义静态 ELF 入口、用户栈、argc/argv 和最小运行时。
- [ ] 提供用户态创建子进程、等待退出状态、终止进程及回收资源的接口；失败创建不得发布半初始化任务。
- [ ] 明确标准输入输出、FD 继承/关闭、共享偏移及错误编码；按 CLI 需要补充目录枚举、路径和文件信息接口。

验收标准：

1. 用户程序携带多个参数启动子程序，子程序收到正确参数，父程序 wait 得到对应 PID 与退出码。
2. 加载失败、非法参数指针或用户程序异常不导致内核崩溃，也不遗留任务、地址空间或文件句柄。
3. 连续运行并回收 100 次短程序后，任务和 FD 数回到基线，内存没有随次数持续增长。
4. 三架构可用同一份最小用户程序源码验证参数与退出契约；架构差异留在启动代码和 ABI 实现中。

### P1-2：完整 CLI 基础系统

范围：将 init、shell 和基本工具放入用户态。内核调试入口可以保留，但不能承担正常用户操作。

- [ ] 用户态 init 启动/恢复 shell、回收孤儿进程；shell 支持参数、当前目录、前台执行及退出状态。
- [ ] 提供列目录、读写/复制文件、建删目录、查看/终止进程、同步和关机等必要工具，以及最小文本编辑能力。
- [ ] 明确控制台行输入、编辑、EOF 和中断语义；按需求补齐 FD 重定向与最小管道，共用已有文件接口。

验收标准：

1. 镜像完全不包含 Desktop、GUI 库和桌面资源，仍能启动进入用户态 shell。
2. 从 shell 创建目录和文本文件、编辑保存、复制读取、运行带参数的程序、查看并终止进程、同步关机；重启后文件保持正确。
3. 重定向能写入文件，管道两端能正确结束并回收资源；输入错误、命令失败或单个应用崩溃后仍可继续执行命令。
4. shell 异常退出后 init 能恢复交互，基础工具不链接 GUI 库，也不依赖图形服务。

### P2：通用显示与输入接口

范围：从文字控制台提取通用设备边界；帧缓冲控制台作为一个客户端保留。优先复用现有 VirtIO 传输与队列实现。

- [ ] 显示接口暴露分辨率、像素格式、stride 和受控缓冲区；统一前台显示/输入所有权及进程退出回收。
- [ ] 输入事件保留按下/释放、修饰键和鼠标信息；文字控制台通过适配层继续提供字符输入。
- [ ] 图形会话期间控制台日志、光标和滚屏不覆盖 GUI；日志仍能经串口或缓冲区查看。

验收标准：

1. 无任何图形服务时，原有文字显示、输入、光标与滚屏继续工作。
2. 用户态显示程序取得显示/输入后正确绘制并接收键鼠事件；正常退出和异常退出都恢复可用控制台。
3. 应用不能借显示接口访问任意 MMIO/物理内存；越界缓冲区和非法请求被拒绝。

### P3：可选 Desktop 最小闭环

范围：先以一个用户态进程承载合成与窗口管理，提供小型 IPC 和 GUI 客户端库；只实现窗口、焦点、移动和关闭等基本操作。

- [ ] 从 shell 显式启动 Desktop；GUI 依赖只随可选桌面软件安装。
- [ ] 明确客户端缓冲区、事件和连接的生命周期；客户端退出时服务回收窗口和相关资源。
- [ ] 将显示/输入会话恢复纳入失败处理，不依赖正常执行 Desktop 的退出代码。

验收标准：

1. Base 和 Desktop 镜像使用同一份内核产物；删除桌面软件后 Base 仍可启动并完成 P1 的 CLI 操作。
2. 用户可从 shell 启动 Desktop，打开两个窗口，切换焦点、移动、关闭；退出 Desktop 后回到可输入命令的 shell。
3. 单个 GUI 应用崩溃不影响其他应用和内核；Desktop 自身崩溃后显示和输入回到命令行。
4. 重复启动/退出 Desktop 后，显示、输入、窗口缓冲区和连接资源均正确归还。

### P4：少量实用图形应用与打磨

范围：先做终端、文件浏览器、文本编辑器，让桌面完成实际任务；不以复杂特效和应用数量作为进度。

- [ ] 图形终端运行同一个用户态 shell，复用终端/进程接口；文件浏览和编辑共用 VFS 与现有文件语义。
- [ ] 统一逻辑坐标、字体度量和缩放规则；文字、光标、命中区域、滚屏及窗口布局一起适配。
- [ ] 统一必要快捷键、焦点提示和错误反馈；空闲窗口等待事件，避免忙轮询。

验收标准：

1. 在终端运行 CLI 工具，在文件浏览器定位文件，在编辑器修改保存，CLI 读取到相同内容；重启后修改保留。
2. 不同窗口尺寸和支持的缩放设置下，文字可读，光标/点击位置准确，滚屏不残留、不越界。
3. 记录内核/镜像大小、启动时间、CLI/桌面空闲内存及 CPU 占用，并据实设置预算；持续交互后资源占用不随操作次数无界增长。

## 三种运行模式的发布门槛

| 场景 | 必须满足 |
| --- | --- |
| 不安装 Desktop | 启动进入 CLI，基础文件、进程、诊断和同步关机功能完整 |
| 安装但不启动 Desktop | CLI 操作不依赖桌面服务，不预先占用图形会话资源 |
| Desktop 运行中 | GUI 可用，CLI 工具仍可经图形终端运行，应用故障隔离 |
| Desktop 正常退出或崩溃 | 显示与输入归还控制台，用户能继续执行命令并再次启动 Desktop |

上述行为都以同一内核为基准。后续修改通用显示、输入、进程或文件接口时，必须考虑这些场景，不能只验收桌面画面。

## 暂缓事项与重新考虑条件

| 事项 | 重新考虑的条件 |
| --- | --- |
| Buddy/CFS 等算法替换、SMP | 已测量出当前分配器/调度器或单 CPU 的具体瓶颈 |
| 完整 fork/COW、动态链接、广泛 POSIX 兼容、多用户 | 明确的目标应用提出需求，最小 spawn/静态程序方案不足 |
| 网络栈与网络应用 | 确定首个实际网络场景；不作为 CLI 或桌面启动的前置条件 |
| 第二种持久文件系统、日志与断电恢复 | FAT 基本语义和正常关机持久化完成，且有明确可靠性需求 |
| GPU 加速、3D、复杂主题、浏览器、Wayland/X11 兼容 | 基本桌面已可用，测量或目标应用证明需要 |
| 广泛真机与新增架构 | 先选定一台机器，明确固件、存储、输入和显示支持范围，再逐项验证 |

现有实验功能可保留，暂缓不意味着删除。真机电源管理需按固件/平台实现：当前 x86 QEMU PIIX4、aarch64 固定 PSCI 调用方式不能视为通用真机支持；riscv64 也需确认固件提供所需 SBI 服务。

## 执行与验证规则

1. P0-1 / P0-2 已完成；下一项具体工作是 **P1-1 用户程序生命周期**，先完善三架构静态 ELF 启动 ABI 和最小 spawn/wait，为独立用户态 init/shell 提供基础。
2. 每项工作记录范围、验收结果和限制；未完成项不因“已有部分底层支持”而勾选。性能预算先测量再制定，不预设缺乏依据的数值。
3. 修改内核或项目规则后，按 [AGENTS.md](../AGENTS.md) 执行三架构 `make check`；内核改动执行受影响的 `TEST=0` 生产构建，共享 MM/调度/trap/执行器改动编译三架构。
4. 不因本路线图自动新增或运行回归测试。只有获得所有者对当前任务的明确授权后，才执行相应测试/QEMU 回归；构建通过不能替代运行时验收。
5. 不为 GUI 引入第二套容器、资源管理或设备传输实现；继续遵守 [命名规范](NAMING.md)、[错误处理与所有权规则](ERROR_HANDLING.md)。
